# v0.10.0 — Pre-1.0 Hardening (detailed plan)

**Authored:** 2026-06-14, after a 5-dimension deep review (agent reliability, `urika upgrade` schema map, cross-surface/UX/a11y, test/verification gaps, security/data-integrity/isolation).
**Status:** Planning. Last release before the v1.0.0rc feature freeze.
**Supersedes** the brief v0.10.0 stub in `dev/plans/2026-05-02-roadmap-to-v1.0.md` (which this expands).

**Theme:** close the gaps v1.0's own promises require, plus the "producer writes it / consumer never surfaces it" and "agent output not validated" bug classes this session kept hitting (report narration, dashboard report link, presentation figures). Feature-complete + trustworthy, not new capability.

**Revised scope/effort:** ~12 dev-days (~2.5 weeks) — larger than the original 1-week stub because the review surfaced real, in-class gaps worth fixing before the freeze. Phases are independently shippable; trim from the bottom (P8–P9) if time-boxed.

## P1 — `urika upgrade` (idempotent project migration)  [v1.0 promise 2; ~2 days]

**Finding (good news):** the schema map shows **almost everything is already load-time tolerant** — readers default missing keys (`ProjectConfig.from_toml_dict`, `RunRecord.from_dict` for `metric_interpretation`/`metrics_with_uncertainty`, `[runtime]`/`[privacy]`/`[memory]` blocks, criteria/methods defensive skips, corrupt-JSON `.corrupt-<ts>` preservation). The `leaderboard.json` `entries→ranking` rename is already auto-migrated in `load_leaderboard`. So `upgrade` is mostly *stamping + a few cosmetic rewrites + detection + tests*, not a deep rewrite.

**Ships:**
1. **Version stamp.** Add `[project] schema_version` to `ProjectConfig` (written on every save; `urika upgrade` stamps it on old projects). This is the idempotency/detection key — there is none today.
2. **`urika upgrade [project|--all]`** command (CLI + REPL/TUI + dashboard button): detect source version (explicit stamp, else infer from field/dir presence per the review's `detect_project_version` heuristic), run the applicable migrations, idempotent (second run = no-op), atomic per-file, prints a summary of what changed.
3. **Migrations that actually rewrite disk:** (a) stamp `schema_version`; (b) rewrite `leaderboard.json` `entries→ranking` on disk (currently only in-memory); (c) optionally regenerate `labbook/notes.md` so pre-v0.8 labbooks gain metric-interpretation rendering. Everything else is a verified no-op (documented).
4. **Migration corpus.** New fixtures beyond the 3 existing (`v030-empty-lockfile`, `v03x-corrupt-progress`, `v040-no-runtime-block`): `v050-pre-labbook`, `v080-pre-research-intent`, `v080-old-leaderboard-entries`, `v090-pre-uncertainty`, `v090-multi-experiment`.

**Acceptance:** a real v0.4-era tree upgrades and passes `urika status`/`inspect`/`run` with no warnings; `upgrade` twice = no diff on the second run; every new fixture round-trips.

## P2 — Dashboard surfaces the v0.9 artifacts (written-but-invisible)  [HIGH — same class as the report-link bug; ~1.5 days]

**Finding (HIGH):** `urika finalize` writes `projectbook/METRICS.md`, `methods/<name>_model_card.md`, and `projectbook/reproduce.ipynb`, and the evaluator writes `experiments/<id>/labbook/evaluation.json` — **none are surfaced in the dashboard.** Same bug class the user just hit with the Final-report link (`pages.py:258-284`, `experiment_detail.html`). They're on disk but invisible; the catch-all route would download `.md`/`.ipynb` as raw files instead of rendering.

**Ships (in `dashboard/routers/pages.py` + templates):**
1. **Render routes + links** for `METRICS.md` and model cards (markdown → `report_view.html`, same pattern as the now-fixed report route; reuse the figure-path rewriter). A "Model cards" listing on the methods page; a "Metrics glossary" link in Final outputs.
2. **`reproduce.ipynb`:** a download link in Final outputs (minimal); optional `nbconvert`-to-HTML view if cheap.
3. **`evaluation.json`:** a "View evaluation" link on the experiment page (render `assessment` + `assumptions_detail` as HTML), so a completed evaluation is viewable, not just re-runnable.
4. **Project-home `has_*` flags** for each so cards only show when the artifact exists.

**Acceptance:** after a real finalize, every generated artifact is reachable from the dashboard with a sensible rendered view (not a raw download), behind the existing auth.

## P3 — Agent-subprocess environment isolation  [HIGH; ~1 day]

**Finding (HIGH, with a concrete incident):** the spawned bundled-`claude` CLI inherits the operator's `~/.claude/` — settings, **plugins, skills, and SessionStart/PreToolUse hooks** — which execute inside agent workers (observed 2026-06-10: a SessionStart hook injected skill instructions into a task-agent transcript and burned turns). `compliance.scrub_oauth_env` covers OAuth + nested-session markers well, but **not** config/plugin/hook discovery.

**Ships:**
1. Force the spawned CLI into a clean config context: pass `--settings` pointed at an empty/isolated settings file (and/or set the CLI's config-home/settings-dir env vars to a temp dir) so operator `~/.claude/settings.json`, plugins, skills, and hooks are NOT loaded. Verify the exact mechanism against the installed `claude` CLI (the claude-code-guide agent or `claude --help`) — this is the one item requiring real-CLI verification.
2. Extend the compliance scrub with any `CLAUDE_CODE_*`/config-home env vars that point the CLI at operator config.
3. Keep Urika's own per-agent CLAUDE-style context (the role system prompts) — only the *operator's global* config is isolated.

**Acceptance:** an agent-worker transcript on a plugin/hook-laden operator machine contains zero operator plugin/skill/hook content; experiments use the same turns whether or not the operator has a loaded `~/.claude/`.

## P4 — Finalize integrity validation (agent-hallucination guards)  [MEDIUM; ~1 day]

**Finding (MEDIUM, "broken reproducibility" class):** the finalizer can emit a `findings.json` whose `final_methods[].script` points at a non-existent file; `run_id`/`experiment_id` that resolve to a *different* experiment (model card then quotes the wrong run's metrics — `model_cards.py:146-157` searches all experiments and silently succeeds); a `reproduce.sh` referencing script names that don't match `findings.json`; or a `requirements.txt` with typo'd packages.

**Ships:** a deterministic post-finalize validation pass (best-effort, surfaced as warnings — never blocks finalize) that checks: every `final_methods[].script` exists on disk; every `run_id`/`experiment_id` resolves to a run *in the named experiment* (warn on cross-experiment fallback rather than silently using it); `reproduce.sh`/`reproduce.bat` invocations reference scripts that exist; `selected_figures` paths exist. Emit a concise `progress("warning", …)` list and (optionally) a `projectbook/.finalize-warnings.txt`. (Defer the `pip install --dry-run` requirements check — needs network — to a later opt-in.)

**Acceptance:** a finalize that produced a dangling script path / cross-experiment run-id surfaces a clear warning instead of shipping a broken model card or reproduce script silently.

## P5 — Atomic state writes + small reliability guards  [MEDIUM; ~0.5 day]

**Finding (MEDIUM):** a few durable state writes are still non-atomic (crash/disk-full → truncation): `experiment.py:78` (`experiment.json` create), `experiment.py:85` (`progress.json` create), `leaderboard.py:119` (`leaderboard.json` write), `project_memory.py:351,523` (memory entry + index). Most other state (registry, session, vault, progress-append) is already atomic.

**Ships:** route those through `write_text_atomic`/`write_json_atomic`. Plus the small **evaluator-narration guard**: if `parse_evaluation` returns `None` *and* the raw output reads as narration, surface it the same way reports now do (the pause-after-3 already exists; this just makes a single skipped check legible).

**Acceptance:** simulated mid-write crash on each of those files leaves the prior valid file intact; an evaluator that narrates produces a clear "evaluation unparseable" signal.

## P9 — Release engineering hardening  [MEDIUM-HIGH leverage; ~1 day]

**Findings:** (a) the e2e smoke is **manual-only**, never a CI/release gate — every bug this session shipped past a green unit suite because the smoke (which would catch them, especially with the new content guards) isn't enforced; (b) the smoke fails hard on transient API hangs (the v0.9.1 600s stream-timeout flake), with no transient-vs-real distinction; (c) the deprecated starlette/httpx `TestClient` shim is a real pending CI break.

**Ships:**
1. Make the e2e smoke a **pre-release gate** — invoke it from `release-to-main.sh` (or a tag-triggered Actions job) so a red smoke blocks the tag; keep `URIKA_SKIP_SMOKE` for intentional overrides.
2. **Transient-failure tolerance** in the smoke: classify a step that failed solely on an `Agent stream timeout`/rate-limit as transient — retry once, and if still failing, mark `TRANSIENT` (non-fatal) distinctly from a real `FAIL`, so a provider hiccup doesn't masquerade as a regression (and vice-versa).
3. Migrate off the deprecated `TestClient` shim (httpx) before it breaks CI.

**Acceptance:** `release-to-main.sh` refuses to tag on a real smoke FAIL; a pure API-hang shows as TRANSIENT not FAIL; CI is clean of the httpx deprecation.

## Test hardening (woven through the phases, not a separate phase)

Each phase ships its own regression pins. Beyond those, add the highest-value "next-bug-of-this-class" tests the review flagged: a mocked-agent **finalize-sequence integration test** (file-write order + every artifact parseable after finalize), **parametrized dashboard artifact-route tests** (all filename variants + fallback chain — the bug class behind the report-link + the P2 artifacts), **adapter stream-timeout → transient** unit tests for OpenAI/Google, and **content tests** for METRICS.md / model cards (right sections, not just non-empty).
