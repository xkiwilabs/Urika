# v0.4.5 — surface parity track

**Authored:** 2026-05-17 (post-v0.4.4.4 audit).
**Slots into:** `dev/plans/2026-05-02-roadmap-to-v1.0.md` —
  between v0.4.4 (shipped) and v0.5.0 (memory phases 2-4, planned).
**Status:** Draft.
**Total horizon:** ~5 dev-days.

This release exists because v0.4 added significant new capability
(dashboard, secrets vault, project memory phase 1, agent commands)
without verifying parity across the four user-facing surfaces
(CLI, TUI, REPL, dashboard). A 2026-05-17 audit found one **blocker**
(dashboard new-project skips the agent Q&A loop), six **important**
gaps (mostly TUI missing commands the other surfaces have, plus
dashboard unlock + REPL unlock), and several **minor** asymmetries.

The discipline: ship parity FIRST so v0.5.0 memory deepening lands
on stable surfaces. Without this, the v0.5.0 cut criterion ("memory
is decision-useful after 10+ experiments") is only verifiable on
the CLI — defeating the cross-surface design goal.

## Why this release exists (not folded into v0.5.0)

Parity is interface plumbing. Memory deepening is feature work.
Mixing them means v0.5.0 ships features that immediately need
parity backfill *anyway*, just one feature at a time. Doing parity
first amortises the cost into one focused release.

Verified non-gaps (the audit's first pass got these wrong; spot-
check confirmed they already work):

- Dashboard advisor chat composer + `POST /projects/{name}/advisor`
  + streaming endpoint — works (`api.py:3371+, 3418+`)
- Dashboard pause button — `run_log.html:38` → `POST
  /api/projects/{name}/runs/{exp_id}/pause` (`api.py:3724+`)
- Dashboard new-experiment modal — `experiments.html:143` HTMX form
- Dashboard summarize button — `project_home.html:55,68`
- REPL has all 39 user-facing commands across `commands.py`,
  `cmd_agents.py`, `commands_run.py`, `commands_session.py`,
  including `cmd_inspect` (L1015), `cmd_update` (L1080) — so REPL
  parity is much better than the first audit pass claimed.

## Ships

### Track 1 — Blocker (D1) ~2-3 days

**Dashboard `POST /api/projects` runs the builder-agent Q&A loop.**

Today the endpoint (`api.py:86-216`) scaffolds the workspace but
explicitly skips the interactive loop — comment at line 98-101
literally says *"The interactive scoping agent loop that `urika new`
runs in a foreground terminal is intentionally skipped here.
Free-text builder instructions are stashed to disk for a future
background-builder integration."*

Plan:

1. Extract `_run_builder_agent_loop` (`src/urika/cli/project_new.py:574`)
   into a runtime-agnostic helper that takes an injectable
   `ask_user` callback. CLI passes `click.prompt`; dashboard passes
   a queue/future-based async callback.
2. New `POST /api/projects/{name}/builder/answer` endpoint —
   user POSTs their answer to the current question; resolves the
   waiting future.
3. New `GET /api/projects/{name}/builder/stream` SSE endpoint —
   streams the agent's questions (and provisional answers) back
   to the wizard UI.
4. New `dashboard/templates/project_builder.html` — wizard-style
   modal that streams questions and POSTs responses. Reuses the
   existing modal macro at `_macros.html:30`.
5. The existing `POST /api/projects` either kicks off the loop in
   the background OR (cleaner) becomes the wizard's "start" call
   that returns a builder session ID for the SSE stream.

Tests:
- `tests/test_dashboard/test_api_create_project.py` — add
  `test_builder_loop_runs_on_dashboard_create`. Mock the agent
  runner, assert it was invoked with the same prompt as the CLI
  invocation.
- `tests/test_cross_interface_parity.py` — add
  `test_builder_loop_invocation_parity`. Same builder-loop dummy
  responses → equivalent on-disk project state from CLI and
  dashboard paths.

in REPL yet either (see R1 below). `/secret` is the hardest

  `--force` equivalent as an interactive confirm).

**REPL: `cmd_unlock`.**

Tests:

## Out of scope for v0.4.5

Deferred to later releases per the v1.0 roadmap:

- **D3 — Project memory CRUD on dashboard.** Already on the v0.5.0
  roadmap (memory phases 2-4). Don't double-pay.
- **D4 — Dashboard venv UI.** Minor; CLI/REPL/TUI users can already
  do this. Defer to v0.9 UX-polish or never.
- **T5 — TUI `/usage`.** Minor; `urika usage` exists on CLI for
  the heavier inspection use case.
- **T6 — TUI `/append-criteria`.** Minor; dashboard has the modal.
- **Knowledge search depth parity.** Functional on all 4 surfaces
  with slightly different UIs — that's a UX choice, not a gap.

## Cut criterion

The release ships only when ALL of:

1. **Dashboard `POST /api/projects` produces a project with the
   same builder-agent artifacts as `urika new`.** Criteria seeded,
   advisor history started, planning suggestions stored. Asserted
   in the cross-parity test, not just response code.

2. **TUI `/inspect`, `/unlock`, `/update`, `/secret` exist and
   surface in tab-completion.** Each delegates to the same shared
   helper the REPL/CLI uses (no parallel implementations to drift).

3. **REPL `cmd_unlock` exists and is mentioned in `/help`.**

4. **The five cross-surface parity tests added in Track 3 pass on
   the full matrix** (linux/macOS/windows × py3.11/3.12) when CI
   re-runs.

5. **No regression in the existing 3395-test suite.** Full pytest
   green under both populated and empty `URIKA_HOME` (which is
   the lesson from the v0.4.4.3 → v0.4.4.4 → c3b1a368 sequence).

## Open questions to resolve before starting

1. **Builder loop refactor scope** — does
   `_run_builder_agent_loop` factor cleanly into a runtime-agnostic
   helper, or is it deeply coupled to `click.prompt` semantics
   (interactive timeouts, `--data` handling, etc.)? Estimate could
   inflate to 4 days if the refactor surfaces hidden dependencies.

2. **Secrets flow on TUI** — modal? Inline? Sub-prompt? No
   precedent for interactive secret entry in the TUI today.
   Want to see the design before committing.

3. **Notification auto-seed parity** — should the dashboard's
   `POST /projects` actually mirror the CLI's seeding behavior, or
   is that CLI behavior an artifact we'd rather remove? Worth
   2 minutes of thought before writing the test.
