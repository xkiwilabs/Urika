# v0.6.0 — GitHub Auto-Backup Design

**Authored:** 2026-05-31 (post v0.5.0.x hotfix train).
**Slots into:** `dev/plans/2026-05-02-roadmap-to-v1.0.md` as v0.6.0
  (the next minor after v0.5.0). Reordered 2026-05-04 to ship before
  the multi-provider v0.7.0 work.
**Status:** Designed; ready for writing-plans.
**Estimated effort:** ~6-7 dev-days.

## Goal

Each Urika project becomes a `git` repo automatically backed up to a
user-configured remote. Scope is **backup**, not collaboration.

**Critical scope choice — Urika never talks to the GitHub API, never
sees a GitHub credential.** The user creates the remote on GitHub /
GitLab / Bitbucket / Gitea / wherever (manually, via `gh repo create`,
via web UI), copies the URL, hands it to Urika. From that point
forward Urika is a `git` shell-out wrapper. The user's existing `git`
auth (HTTPS+PAT in OS keyring, SSH key, `gh`-stored credential —
whatever already makes `git push` work on their machine) does all the
authentication.

This is the **thin design**. The thicker "Connect GitHub" experience
(device-flow OAuth, dashboard Connect button, audit log) is preserved
in `dev/archive/2026-04-30-github-integration.md` as a v1.1+ surface
if real demand surfaces.

## Locked decisions (brainstorm 2026-05-31)

1. **Scope = thin.** Zero auth surface; pure `git` shell-out (+
   optional `gh` CLI for `--create`). Provider-agnostic implementation.
2. **Pre-commit secret scan = yes, abort on hit.** Regex sweep of
   staged blobs for known token shapes before every commit. Match →
   abort, don't commit, don't push.
3. **Auto-push default events =
   `["run", "finalize", "build-tool"]`.** Significant work units;
   skips `report`/`present`/`memory` (low-signal narrative) and
   `advisor`/`evaluate` (mid-experiment).
4. **Commit message = `urika:` prefix + structured trailer.** No
   `Co-Authored-By`. Author is the user's `git config user.*`.
5. **.gitignore = researcher-safe defaults.** Excludes
   `.urika/`, common Python build/venv dirs, PEM/SSH/dotenv files,
   AND research data conventions (`data/raw/`, `*.parquet`, `*.h5`,
   `*.pkl`, `*.joblib`).
6. **Push failure handling = print + warn + continue.** No retry, no
   queue. The local commit succeeds; the next manual or auto push
   retries naturally.

## Module layout

```
src/urika/
  core/
    git.py              # pure git wrapper (subprocess) +
                        # _SecretScanner + _Gitignore writer
  cli/
    github.py           # urika github init / push / status / pull
  dashboard/
    routers/
      api.py            # +4 routes: /git/{status,push,log,init}
    templates/
      git.html          # read-only Git tab
```

Why this layout (and not `src/urika/integrations/github/...` from the
archive): the thin design has no auth, no API client, no audit log, no
queue. Three files is enough. The `core/git.py` boundary keeps the
subprocess plumbing testable in isolation; the CLI module just maps
Click commands onto it; the dashboard just adds routes.

## CLI surface

### `urika github init <project> [--remote URL]`

Initialise (or re-initialise idempotently) the project as a git repo.

- Runs `git init` if `.git/` is missing.
- Writes `.gitignore` (see template below) if not present; otherwise
  leaves the user's customisations alone.
- `--remote URL` runs `git remote add origin <URL>` (or `set-url` if
  one exists). Pre-condition: the user has already created the empty
  remote repo somewhere with a working URL.
- Stages all tracked content (`git add -A`) and creates an initial
  commit `urika: initial project state` if there's anything to commit.

### `urika github init <project> --create [--public]`

Uses the `gh` CLI to create a fresh private (default) or public GitHub
repo named after the project, set the remote, and do the first push in
one shot:

```
gh repo create <project-name> --private --source <project-dir> --push
```

**Urika never sees a GitHub credential** — `gh`'s own stored token
does the work. Graceful fallback when `gh` isn't installed or authed:

```
$ urika github init my-project --create
  ✗ gh CLI not found (or not authenticated).
  Install gh:  brew install gh  /  apt install gh  /  https://cli.github.com
  Authenticate: gh auth login
  Alternative: create the repo manually on GitHub, then re-run with
               `urika github init my-project --remote <URL>`.
```

Exit code 2 (usage / dependency error), no partial state left behind.

### `urika github push <project>`

Manual push: `git add -A && git commit -m "<auto-message>" && git push`.
Same secret scan + commit format + failure handling as auto-push (see
below). If there's nothing to commit, `git push` runs on the existing
HEAD anyway (in case earlier commits were never pushed).

### `urika github pull <project>`

`git fetch && git merge --ff-only origin/<branch>`. Refuses on
divergence — print the diff between HEAD and `origin/<branch>` and
tell the user to merge / rebase manually. We don't auto-merge.

### `urika github status <project>`

Prints: remote URL, current branch, last-push timestamp + SHA, recent
commit count, uncommitted-file count, last 5 `urika-event:`-tagged
commits. Read-only.

### `urika new <name> --github [--public]`

Opt-in at project-creation time. When `--github` is passed, runs
`urika github init <name> --create [--public]` after the project
wizard's `write_project()` returns. The wizard's interactive flow
gains the question "Create a private GitHub repo for this project?
[Y/n]" if `gh` is detected. When `--github` is omitted and the global
preference (below) isn't set, no git init happens (current behavior).

### Global default: `[preferences] github_auto_create = true`

In `~/.urika/settings.toml`. Every `urika new` defaults to creating a
remote without re-prompting. Override per invocation with
`--no-github`. Dashboard New Project modal gets a matching checkbox.

```toml
[preferences]
github_auto_create = true
github_auto_create_visibility = "private"  # "private" | "public"
```

## Per-project settings (`<project>/urika.toml`)

```toml
[github]
auto_push = false                  # opt-in
auto_push_after = ["run", "finalize", "build-tool"]
gitignore_extra = []               # additional patterns user wants
                                   # excluded
```

That's it for v0.6. No `auto_commit_on_event`, no
`commit_author = "user"|"urika-bot"` selector, no `dry_run` (use
`urika github push` manually if you want a sanity check), no
`include_runs` toggle. YAGNI.

## Auto-push hook

Fires at the **end** of each listed CLI command (after the command's
normal output, before the process exits). Sequence:

1. **Secret scan** — `urika.core.git.SecretScanner` runs a regex
   sweep on every staged blob (`git diff --cached --name-only` →
   read each file via `git show :<path>` to get the staged content).

   Patterns (case-sensitive):
   - `sk-ant-[A-Za-z0-9_\-]{32,}` — Anthropic API key
   - `sk-[A-Za-z0-9]{40,}` — OpenAI / generic
   - `ghp_[A-Za-z0-9]{36}` — GitHub personal access token
   - `gho_[A-Za-z0-9]{36}` — GitHub OAuth
   - `ghu_[A-Za-z0-9]{36}` — GitHub user-to-server
   - `ghs_[A-Za-z0-9]{36}` — GitHub server-to-server
   - `AKIA[0-9A-Z]{16}` — AWS access key ID
   - `[A-Za-z0-9/+=]{40}` preceded by `aws_secret_access_key` (case-
     insensitive within 100 chars) — AWS secret access key

   On a match:
   ```
   ✗ [urika:secret-detected] Potential secret in <path>:<line>
     Match: sk-ant-...XYZ8  (preview, last 4 chars only)
     Aborted commit. Either remove the secret from <path> or add
     <path> to .gitignore, then re-run.
   ```
   Exit code 3. **No commit, no push.** The local working tree is
   untouched.

2. **Commit** — `git add -A && git commit -m "<auto-message>"`.

3. **Push** — `git push`. On failure (any non-zero exit from `git
   push`), print:
   ```
   ⚠ urika github auto_push: failed
     <stderr from git verbatim>
     Retry manually with `urika github push <project>`.
   ```
   The local commit is preserved; the next push retries naturally.

If `auto_push = false`, only steps 1 and 2 are conditionally skipped
based on whether the user has configured the manual `urika github push`
flow separately. Auto-push is the only event-driven path.

## Commit message format

```
urika: experiment exp-003-paired-t completed (paired-t, p=3.4e-37)

Project: dht-target-selection-v2
Turn: 3/3
Cost: $0.12

urika-event: experiment_complete
urika-version: 0.6.0
```

Auto-message templates:

| Event | Subject |
|---|---|
| `experiment_complete` (after `urika run`) | `urika: experiment <exp_id> completed (<best_method>, <best_metric>)` |
| `experiment_failed` | `urika: experiment <exp_id> failed (<error_class>)` |
| `finalize_complete` (after `urika finalize`) | `urika: finalized project (<best_method>, <runs_count> runs)` |
| `tool_added` (after `urika build-tool`) | `urika: added tool <tool_name>` |
| `manual` (`urika github push`) | `urika: project state (<runs_count> runs across <experiment_count> experiments)` |

**No `Co-Authored-By:` trailer.** Author is the user's
`git config user.*`. Finding Urika-authored commits later:
`git log --grep '^urika-event:'`.

## `.gitignore` template

Written verbatim by `urika github init` if no `.gitignore` exists.

```
# Urika internal state — never commit (secrets, sessions, meta)
.urika/
*.lock

# Python
__pycache__/
*.pyc
.venv/
venv/
.tox/

# Credentials / private keys (never commit, even if user opts out
# of other defaults)
.env
*.pem
*.key
*_rsa
*_ed25519

# Research data — researcher-safe default exclusion. Delete these
# lines (or override via [github] gitignore_extra in urika.toml) if
# your project's raw data is safe to commit.
data/raw/
*.parquet
*.h5
*.pkl
*.joblib
```

If the user pre-existed a `.gitignore`, Urika appends a `# urika:
managed block` between markers:

```
# >>> urika: managed block — do not edit between markers >>>
.urika/
...
# <<< urika: managed block <<<
```

Re-running `urika github init` replaces the block in place; the rest
of the user's `.gitignore` is untouched.

## Dashboard Git tab

Per-project page at `/projects/{name}/git`, sidebar link between
Methods and Knowledge.

Read-only data:
- **Remote URL** (with masked-preview for any embedded token —
  `https://ghp_****@github.com/user/repo` → `https://ghp_****@github.com/user/repo`).
- **Current branch** + **last-push timestamp** + **last-push SHA**.
- **Uncommitted-changes count** from `git status --porcelain | wc -l`.
- **Recent commit log** (last 10): SHA · subject · `urika-event:`
  chip (if tagged) · age.

Interactive:
- **"Push now"** button → `POST /api/projects/{name}/git/push`
  (Origin-checked + auth-gated like the rest of the dashboard).
- **"Init repo"** flow when no `.git/` exists yet — modal with the
  same choices as the CLI (`--remote URL` or `--create`).

Out of scope for the dashboard in v0.6:
- Pull (use the CLI; cross-origin git pull mid-experiment is a
  recipe for confusion).
- Branch switching, diffs, commit detail views, conflict resolution.
  Those are git-client territory, not Urika's surface.

## API routes (new in `dashboard/routers/api.py`)

```
GET    /api/projects/{name}/git/status   → JSON { remote, branch, last_push, dirty_count, recent: [...] }
POST   /api/projects/{name}/git/push     → JSON { ok, pushed_sha, error? }
GET    /api/projects/{name}/git/log      → JSON { commits: [{sha, subject, event, ts}, ...] }
POST   /api/projects/{name}/git/init     → JSON { ok, remote_set? }    body: { remote?, create?, public? }
```

All POSTs are CSRF-Origin-checked (v0.4.5.1 middleware), auth-token-
gated (v0.4.5.1 default), and rate-limited only by the user's `git`
binary (push can take seconds).

## Event wiring

Auto-push hooks into the end of each CLI command rather than into the
orchestrator's `on_progress` stream. The orchestrator stays untouched.

Implementation: each command in `cli/` that's in `auto_push_after`
adds a tiny `_maybe_auto_push(project_dir)` call as the last thing
before exit. That helper reads `urika.toml`, checks `auto_push`, then
calls into `urika.core.git`. Five call sites in v0.6:

- `cli/run.py` — end of `urika run`
- `cli/agents_finalize.py` — end of `urika finalize`
- `cli/agents.py` — end of `urika build-tool`
- (REPL/TUI equivalents inherit via the existing command-dispatch
  pattern — same `_maybe_auto_push` call wrapping `ctx.invoke(...)`)

## Module API: `urika.core.git`

Public surface:

```python
def is_git_repo(project_dir: Path) -> bool: ...
def init_repo(project_dir: Path, remote: str | None = None) -> None: ...
def add_remote(project_dir: Path, url: str, name: str = "origin") -> None: ...
def write_gitignore(project_dir: Path, extra_patterns: list[str] | None = None) -> None: ...
def commit_all(project_dir: Path, message: str) -> CommitResult: ...
def push(project_dir: Path) -> PushResult: ...
def pull(project_dir: Path) -> PullResult: ...
def status(project_dir: Path) -> GitStatus: ...
def recent_commits(project_dir: Path, limit: int = 10) -> list[GitCommit]: ...
def scan_for_secrets(project_dir: Path) -> list[SecretMatch]: ...    # internal but exposed for testing
```

Result dataclasses are small (success bool + sha + error message). All
functions are pure subprocess wrappers — no in-memory git state, no
caching. Errors come back as values, not exceptions, so callers can
print remediation hints cleanly.

The `gh` integration lives in a single `gh_create_repo(project_dir, name, public: bool) -> GhCreateResult` function that wraps `gh repo create`. Returns a `GhCreateResult(ok, error, install_hint)` — the CLI prints
`install_hint` when `ok is False` and `gh` is missing.

## Testing strategy

Unit tests (Linux + macOS + Windows CI):
- `tests/test_core/test_git.py` — every public function against a
  `tmp_path` with a bare git repo as the remote. No GitHub needed.
- `tests/test_core/test_git_secret_scanner.py` — fixture files with
  embedded `sk-ant-...`, `ghp_...`, etc.; assert each pattern is
  caught; assert clean files pass.
- `tests/test_cli/test_github_*.py` — `urika github init`, `push`,
  `status`, `pull` against a tmp_project + tmp_bare_remote fixture.
- `tests/test_dashboard/test_api_git.py` — the 4 new routes.
- `tests/test_dashboard/test_pages_git.py` — Git tab renders.

Integration test (opt-in, `pytestmark = pytest.mark.integration`):
- `tests/test_integration_github_push.py` — `urika new --no-github`,
  `urika github init --remote <local-bare>`, set `auto_push=true` in
  urika.toml, `urika run --max-turns 1`, assert the bare remote has
  the new commit with the right `urika-event:` trailer.

No tests touch real GitHub. The bare-remote pattern is enough.

## Cut criterion

The release ships only when ALL of:

1. **Init flow works against a manually-created remote.**
   `urika github init <project> --remote <URL>` writes the
   `.gitignore`, creates the initial commit, pushes successfully on
   a manual `urika github push`.

2. **`--create` works when `gh` is installed and authed.**
   `urika github init <project> --create` creates a private repo on
   GitHub, sets the remote, and lands the first push — verified by
   running it against the real GitHub via the operator's account
   (the only step that touches real GitHub in the entire release).
   Falls back gracefully with the install hint when `gh` is absent.

3. **Auto-push fires within 60s of `urika run` completion** on a
   project with `auto_push = true`. Verified by the
   integration test against a local bare remote.

4. **Pre-commit secret scan catches `sk-ant-XXX` planted in a test
   fixture** and aborts the commit. Verified by a unit test with a
   fixture file containing each known pattern.

5. **Dashboard Git tab renders correctly** across the open / hybrid /
   private project shapes. Manual "Push now" button works.

6. **All four `git push` failure modes** (network down, auth expired,
   non-fast-forward, remote unreachable) print the underlying git
   stderr verbatim and leave the local commit intact. Manual
   `urika github push` retries successfully after the underlying
   condition clears.

7. **Full unit suite green.** No regressions in the existing 3614
   tests; net new ~30-40 tests for git wrapper + secret scanner +
   CLI + dashboard.

## Out of scope for v0.6.0

Deferred to v1.1+ ("Connect GitHub" thick experience):

- Device-flow OAuth, dashboard Connect button.
- GitHub-API-driven repo creation (use `gh` CLI instead).
- Audit log viewer in the dashboard.
- Offline commit queue + retry-next-event.
- Per-event commit-author switching between user and `urika-bot`.
- `dry_run` mode that stops before push.
- README auto-management (let `readme_generator` rewrite on every
  event).
- Branch-per-experiment / auto-PR workflows.
- LFS support for large artifacts.

Out of scope entirely (won't ship in any release):

- Multi-remote per project (Urika manages exactly one `origin`).
- Squash / rebase / interactive history rewriting (that's the user's
  `git` client).
- Conflict resolution UI in the dashboard.

## Risks

1. **Secret scanner false positives.** The patterns are conservative
   but a base64 blob with the wrong shape could trigger `sk-` /
   `ghp_`-prefixed regexes. Mitigation: the scanner reports the
   `file:line` and last 4 chars; the user can verify and add to
   `.gitignore` if it's not actually a secret. Could not find a
   high-entropy heuristic that's both cheap and precise; the
   prefix-pattern approach is the standard in `git-secrets`,
   `truffleHog`, etc., and is good enough.

2. **`gh repo create` rate-limit.** Unauthenticated GitHub API has a
   60/hr limit; `gh`'s authenticated path is 5000/hr. Users who hit
   `--create` more than ~50 times in an hour (test scripts, CI) will
   see a 403. Mitigation: surface `gh`'s own error verbatim and
   point at `gh auth status`.

3. **Multi-remote drift.** If a user adds a second remote manually
   (`git remote add upstream <url>`), Urika's `push` only pushes to
   `origin`. Acceptable — Urika manages exactly one remote, the user
   can manage extras with raw `git`.

4. **Auto-push hook recursive trigger.** A push event must NOT
   re-trigger another push (infinite loop). The implementation
   should `_maybe_auto_push` exactly once per command invocation,
   guarded by a process-local flag. Tested explicitly.
