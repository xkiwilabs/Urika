## Ships

### Track 1 — Phase 1 read-injection completion + Phase 2 dashboard surface (~1.5 days)

The smallest gap: complete the Phase 1 read injection, then close the
Phase 2 dashboard hole. Foundation for Tracks 2 + 3.

### Track 2 — Phase 3: curator agent + auto-trigger (~2-3 days)

The biggest piece. New agent role + orchestrator hook + CLI/REPL/
dashboard surfaces.

**Curator agent:**

- New `src/urika/agents/roles/memory_curator.py` modeled on the
  existing role pattern (system prompt + `build_config`).
- System prompt at
  `src/urika/agents/roles/prompts/memory_curator_system.md`:
  - Reads the current memory directory contents.
  - Emits structured decisions: merge entry-A-into-entry-B, archive
    entry-C, flag entry-D-as-stale, flag contradiction-between-E-and-F.
  - JSON-block output for parsable decisions, matching the existing
    advisor / planning conventions.
- Add to `AgentRegistry` so `registry.get("memory_curator")` works.

**Curator dispatch:**

- New `src/urika/core/memory_curator.py` (or extend
  `project_memory.py`) with:
  - `run_curator(project_dir, runner) -> CuratorResult` — invokes
    the agent, parses decisions, applies them (merge / archive /
    flag) to disk.
  - `count_entries(project_dir) -> int`
  - `estimated_inject_tokens(project_dir) -> int` — `len(text.encode("utf-8")) // 3.5`
    (Decision 2: conservative byte-heuristic, no new dependency).
- Archive layout: `memory/archive/<YYYY-MM>/<filename>` (per design).
- `.trash/` distinct from `archive/` — trash is user-deleted, archive
  is curator-aged-out.

**Auto-trigger:**

- Soft cap = 30 entries OR 5K injected tokens (design constant). When
  exceeded, `load_project_memory` returns the memory but ALSO flips a
  SESSION-SCOPED flag the orchestrator reads at next agent invocation
  to run the curator IN DRY-RUN mode (Decision 4). The curator emits
  its proposed decisions (merge / archive / flag) as a notice on the
  agent's text stream + the dashboard memory page; nothing is applied
  without `urika memory curate --apply` or the dashboard "Apply"
  button. The session-scoped flag prevents re-firing for the same
  over-budget state in the same session. (Curator never runs inline
  mid-injection — too slow for every agent turn.)
- Hard cap = 10K tokens. Past that, `load_project_memory` returns a
  truncated body + a `## Project Memory (over budget — run urika
  memory curate)` marker that surfaces to the user via the agent's
  text output.
- Trigger point: orchestrator's pre-turn hook in `orchestrator/loop.py`.
  Existing pattern: there's already a pre-turn check for criteria
  status; the curator-trigger slots in alongside.

**Surfaces:**

- CLI: `urika memory curate <project>` (dry-run by default — prints
  proposed decisions) and `urika memory curate <project> --apply`
  (commits them). `cli/memory.py` extension.
- REPL: `/memory curate` (dry-run) and `/memory curate --apply` via
  `cmd_memory` dispatcher.
- TUI: inherits via REPL registry.
- Dashboard: "Curate now" button on the memory page runs dry-run and
  renders proposed decisions; a separate "Apply" button (gated by a
  confirm dialog) commits them. Both stream progress via SSE
  (existing pattern from the builder wizard work).

**Tests:**
- `tests/test_agents/test_memory_curator_role.py` — role registration,
  config build.
- `tests/test_core/test_memory_curator.py` — duplicate-merge, archive,
  contradiction-flag behavior against a hand-built memory corpus.
- `tests/test_orchestrator/test_curator_auto_trigger.py` — soft-cap
  fires curator at next turn; hard-cap truncates injection.

### Track 3 — Phase 4: archive viewer + diff view (~1-1.5 days)

User-facing introspection on the curator's output.

**Archive viewer:**

- CLI: `urika memory archive <project> [--month YYYY-MM]` — lists
  archived entries; with `--month`, drills into one month.
- REPL: `/memory archive` (list) / `/memory archive YYYY-MM` (drill).
- Dashboard: "Show archived" toggle on the memory page that includes
  archived entries (greyed out, with archive-month label).

**Diff view:**

- CLI: `urika memory diff <project> <from> <to>` where `from` and
  `to` are timestamps (ISO 8601) or relative ("yesterday", "1w ago").
  Reads filesystem MTIMES (Decision 3) across the memory dir +
  `.trash/` + `archive/` and shows entries added/removed/archived
  between the two points. Per-file granularity is a known limit —
  in-place rewrites lose their prior body; users who need that level
  of history wait for v0.6.0 GitHub auto-backup.
- REPL: `/memory diff <from> <to>`.
- Dashboard: timeline view at `/projects/{name}/memory/history` —
  sparkline of entry count over time + per-day add/remove counts +
  click-into-date for diff against today.

**Per-project `auto_capture` toggle:**

- Dashboard settings page: checkbox writes `[memory] auto_capture =
  true|false` to `urika.toml`. Already supported by the core helpers
  (`is_enabled` reads it); just need the UI.

## Cut criterion

The release ships only when ALL of:

1. **Advisor agent injects project memory** — verified by import
   check + behaviour test that asserts memory content reaches the
   advisor's prompt.

2. **Dashboard memory page exists** — list / add / edit / delete
   round-trip works from the browser, parity with CLI behavior.

3. **A project that runs ~10 hand-seeded experiments has its
   memory directory readable** — concretely: take the
   ``project_dht_target_selection`` real project, add ~10
   entries spanning preferences / decisions / instructions /
   references, run the curator, observe ≤ 15 entries after
   curation with no duplicates and at least one contradiction
   flagged (per the design's success scenario).

4. **Memory injection token cost stays under 5K tokens** for a
   project with up to 30 entries; soft-cap auto-trigger fires
   the curator at next agent invocation when exceeded.

5. **Hard cap at 10K tokens** is enforced — verified by injecting
   a synthetic 15K-token memory corpus and observing the truncate-
   plus-marker behavior.

6. **All four surfaces support curate / archive / diff / CRUD**
   commands. Cross-parity tests in
   `tests/test_cross_interface_parity.py` pin them.

7. **Full pytest green** under `URIKA_HOME=/tmp/empty/` (current
   baseline: 3442 passed / 2 skipped — net new tests ~20-30 in
   this release).

## Out of scope for v0.5.0

- **Read-memory tool call** (per the design's "v2 consideration" —
  agents currently get memory as a system-prompt prefix only; no
  on-demand `read_memory(topic)` tool call).
- **Memory-aware advisor turn-summarization** that uses memory to
  shape what gets archived vs kept (design didn't lock this).
- **Cross-project memory** (design explicitly says no — memory is
  project-scoped).

## Decisions (resolved 2026-05-31)

1. **Report agent injection — INCLUDED in Track 1.** Mirror the
   `planning_agent.py:48-55` injection block into `report_agent.py`
   (and `advisor_agent.py`). The v1 read-side closes here:
   planner + advisor + report all see project memory; task /
   evaluator stay out (no behavioural rationale to inject for those
   roles). Cost ~10 min + 1 behaviour test per agent.

2. **Token counting — byte-heuristic, conservative (`bytes / 3.5`).**
   No new dependency. The denominator is `3.5` rather than `4` so the
   estimate biases UP — non-Latin scripts / code don't sneak under
   the cap, and the failure mode is "curator fires slightly early"
   which is harmless. Risk #3 mitigation baked into the default.
   Re-evaluate against tiktoken or the Anthropic SDK tokenizer only
   if real usage shows the estimate diverging materially.

3. **Memory diff source of truth — mtime.** Reconstruct the
   timeline by stat-ing the memory dir + `.trash/` + `archive/` and
   sorting by mtime. No git dependency (works on projects without a
   GitHub remote). Per-file granularity is a known limitation — a
   rewrite of an existing entry loses its prior body — accepted for
   v0.5; the `archive/` snapshots and curator decisions log give
   enough recovery surface for the realistic use cases.

4. **Curator auto-trigger — once per session, DRY-RUN by default.**
   When the soft-cap (30 entries OR 5K injected tokens) is exceeded,
   the orchestrator's pre-turn hook flags the curator to run at the
   next agent invocation in that session, EMITS its proposed
   decisions (merge / archive / flag), and surfaces them as a notice
   in the agent's text output and on the dashboard memory page.
   Nothing is applied without an explicit `urika memory curate
   --apply` (or the dashboard "Apply" button). The session-scoped
   flag prevents re-running for the same over-budget state. Risk #1's
   safety mitigation is the default, not an extra mode.

## Risks

1. **Curator agent prompt complexity.** The curator needs to make
   semantic merge decisions ("entry A and entry B both say the
   user wants tree models — merge"). Risk of false positives
   (merges that shouldn't merge) is high without careful prompt
   engineering. **Mitigation baked in via Decision 4:** dry-run is
   the default — curator emits decisions but never mutates the
   memory dir without `--apply`. False-positive blast radius is
   zero by construction. The ~0.5 day this would have added is
   already in the Track 2 budget.

2. **Auto-trigger interaction with the v0.4.4.3 stream timeout.**
   Curator runs at start-of-turn; if it stalls (long memory dir,
   slow model), the per-stream `URIKA_AGENT_STREAM_TIMEOUT` (600s
   default) catches it. Should be fine; verify in Track 4 parity
   tests.

3. **Token-counting heuristic underestimate.** Byte-heuristic
   (bytes/4) is OK for English; can underestimate for code or
   non-Latin scripts in user-supplied memory. Mitigation: count
   conservatively (bytes/3.5 — assume the worst case) for budget
   decisions; switch to tiktoken if user complaints surface.
